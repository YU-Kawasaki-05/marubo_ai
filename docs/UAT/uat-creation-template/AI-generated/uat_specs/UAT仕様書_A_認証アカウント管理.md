## 2. カテゴリ概要

認証・アカウント管理カテゴリは、Supabase Auth（Google OAuth）を使用したユーザーログイン・ログアウト・セッション管理を対象とする。許可リスト（`allowed_email` テーブル）の `status` に基づいてアクセス可否を判定し、ロール（`student` / `staff`）に応じてリダイレクト先を制御する。本カテゴリはシステム全体のセキュリティ基盤であり、テスト優先度は「最高」。

**前提環境:**
- テスト用 Google アカウントが複数用意されていること（active生徒 / active スタッフ / pending / revoked / 未登録）
- テスト環境の URL: `https://marubo-ai.vercel.app`（または検証環境 URL）

**テスト用アカウント準備チェックリスト（任意・推奨）:**

| アカウント種別 | メールアドレス例 | `allowed_email` ステータス | 用途 |
|--------------|---------------|--------------------------|-----|
| student_active | student_active@gmail.com | `status='active'`, `label='テスト生徒'` | TC_A_001, TC_A_006, TC_A_008 |
| staff_active | staff_active@gmail.com | `status='active'`, `app_metadata.role='staff'` | TC_A_002, TC_A_007 |
| student_pending | student_pending@gmail.com | `status='pending'` | TC_A_004 |
| student_revoked | student_revoked@gmail.com | `status='revoked'` | TC_A_005 |
| student_unlisted | student_unlisted@gmail.com | 未登録 | TC_A_003 |

> 上記アカウントは Supabase Dashboard の `allowed_email` テーブルを直接編集して準備すること。

#### TC_A_008: セッション失効時の SessionExpiredModal 表示（正常系）

| 項目 | 内容 |
|------|------|
| **テストケースID** | TC_A_008 |
| **業務ID** | A-06 |
| **テスト区分** | 正常系 |
| **優先度** | 中 |
| **前提条件** | active 生徒としてログイン済み。Supabase Dashboard で JWT 有効期限を短縮できる、または長時間放置が可能な環境 |
| **ステータス** | ⏳ 後日実施（JWT 自然失効の待機が必要なため、他のテスト完了後にまとめて実施） |

**操作手順:**

> ⚠️ **Cookie / Local Storage の手動削除ではこのテストは再現できません。**
> Supabase SDK はセッションをメモリ上にも保持するため、ストレージを削除しても `SIGNED_OUT` イベントは発火しません。
> リロードすると middleware が `/login` にリダイレクトするため、モーダルが表示される機会がありません。

**方法 A: JWT 有効期限の短縮（推奨・迅速）**

1. Supabase Dashboard → Authentication → Settings → JWT Expiry を `60`（秒）に変更して保存する
2. active 生徒としてチャット画面（`/chat`）にログインする
3. 約 60 秒待機する（JWT が失効し、SDK がリフレッシュを試みて失敗する）
4. チャット画面で何か操作（送信ボタンクリック、会話選択など）を行う
5. 表示されるモーダルを確認する
6. **テスト終了後、JWT Expiry を元の値（デフォルト: 3600）に戻す**

**方法 B: 自然失効（待機が必要）**

1. active 生徒としてチャット画面（`/chat`）にログインする
2. そのまま JWT 有効期限（デフォルト 1 時間）が切れるまで放置する
3. チャット画面で何か操作を行う
4. 表示されるモーダルを確認する

**期待結果:**

| 確認ポイント | 期待値 | 確認方法 |
|------------|--------|---------|
| SessionExpiredModal 表示 | 「セッションが切れました」モーダルが表示される | 画面確認 |
| 再ログインボタン | モーダル内に「ログイン画面へ」ボタンが表示される | 画面確認 |
| 再ログインボタン押下 | `/login` に遷移する | URL 確認 |
| 白画面にならない | Error Boundary により白画面にならず、適切な UI が表示される | 画面確認 |

### IT_A_002: 許可リストステータス変化時のアクセス制御変化

| 項目 | 内容 |
|------|------|
| **シナリオID** | IT_A_002 |
| **目的** | `status` 変更がリアルタイムにアクセス制御に反映されることを確認（F-03 と連携） |

**シナリオ手順:**

1. active 生徒としてログイン済みの状態にする
2. スタッフが管理画面から対象メールの `status` を `revoked` に変更する
3. 生徒側でページリロードまたは新しい操作（API コール）が発生した際に、アクセスが拒否されることを確認する

**期待結果:** `status='revoked'` 変更後に、該当ユーザーがチャット機能を使用できなくなる

> **注記**: ステータス変更の反映はページリロードまたは次回 API コール時に行われる。変更直後にリアルタイムで反映されない場合があるため、ページリロード後に再確認すること。反映に最大数秒のタイムラグが生じる可能性がある。

## 5. 備考

- Google OAuth の実際の認証には Google アカウントが必要。テスト用アカウントを事前に準備すること
- Supabase Dashboard で `allowed_email` テーブルを直接編集することで、各ステータスのテストデータを作成できる
- `TC_A_008` のセッション失効テストは Cookie / Local Storage 削除では再現不可（SDK がメモリ上にセッションを保持するため）。Supabase Dashboard で JWT Expiry を短縮するか、1 時間の自然失効を待つ必要がある
- セキュリティヘッダーの確認は K カテゴリ（TC_K_008）で実施するため、本カテゴリでは省略
- pending / revoked エラー時のメッセージ文言は api.md の正式定義に従う（「利用開始準備中です」/ 「アカウントが停止されています」）
